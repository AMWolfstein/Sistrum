### Native and Media3 transition comparison

- Native `nativeBeginCrossfade` swaps active/preloaded slots and emits `CrossfadeStarted`; its output callback retires the outgoing slot at fade completion. `LegacyNativeEngine.drain` maps that event to the coordinator. Media3 `startFade` swaps slots and emits `TransitionStarted`; the transition tick waits for the processor curve and queued output to drain before releasing A. Both retain queue/statistics/session promotion at fade start and defer i+2 preload until the fade ends.
- Native snaps call `snap_fade`; Media3 snaps cancel the delayed B start, stop A, force B's gain and flush B's queued audio. Media3's processed-clock lead and incoming start calibration are existing ADR-003 behavior, not equivalent hardware timing assumed from the native implementation. Relevant device test sources cover timing and snap output, but were not executed here.
- M2 intentionally changes only Media3 automatic fades between different tracks: outgoing tail moves the trigger; incoming lead moves B's final restart and processing-clock origin. Native `PlayerEngine.automaticFadeDurationMs` still calls the original 001 functions and its silence-option setter is a no-op. Manual skips, same-item repeats, crossfade-off playback and missing-profile timing retain the documented policy. No additional loss of native start/finish/snap or queue-update behavior was confirmed in this range.

### Race and lifecycle evidence / limits

- **Next/previous versus automatic promotion:** coordinator actions drain pending engine events before reading/mutating the queue; commands and ticks share the single drainer. Media3 outgoing callbacks cannot advance the current queue. This establishes the intended ordering in code; physical presses at the boundary still need check 1.
- **Queue edits while B prepares or a fade runs:** queue mutation paths snap running transitions, then reconcile the successor. Media3 serializes slot/controller work on the factory looper and releases obsolete prepared B. `canPreloadNext` prevents i+2 replacing A mid-fade. Existing characterization tests inspect these paths; new profile loading remains in the command transaction rather than launching an independent stale-result writer.
- **Settings versus prepared/running fade:** silence option changes reach the controller without altering a running command. The lead position is retained during preparation and consulted when `beginFade` constructs the command, so OFF/ON before fade start uses the current option. Running fade processors retain their captured duration. Night mode deliberately remains live through one volatile reader shared by A/B and replacement players.
- **Callbacks after track change/release:** delayed B start checks player identity and transition phase; release removes the callback, slot listeners and analytics listeners. Close removes transition/focus runnables and cancels the new Night mode scope. Artwork and Mood Radio publication remain in the serialized coordinator. No new competing StateFlow writer or duplicate listener registration was found.
- **Session/service:** framework MediaSession is created in `onCreate`, released during ordered teardown; generation guarding prevents an older teardown clearing a new session's published state. Manifest declares media playback permission/type; every service start promotes foreground before command work. Paused state remains active under existing policy; there is no new M2 pause-expiry policy. Notification callbacks and media buttons reach the same coordinator. There is no MediaBrowserService/Android Auto browsing implementation to validate in this milestone (ADR-006 defers session migration).
- **Focus/routes:** explicit service focus listener dispatches transient pause/resume, duck/restore and permanent pause; players do not independently own focus. Permanent loss remains paused pending explicit user resume, as characterized in 001. Becoming-noisy dispatches pause. Actual OS callback delivery/routing remains unverified here.
- **Persistence/process/UI:** saved queue, position and shuffle/repeat restore through `restoreSaved`, preparing paused; periodic position saves bound what can survive abrupt death. Preferences persist independently; profiles are loaded from current-version, same-fingerprint analysis documents, with logged legacy fallback on read failure and cancellation propagation. Playback belongs to the service, not the activity. `playCurrent` closes the old engine before constructing the selected replacement; the new preference observer is cancelled by engine close. Abrupt kills, OEM restrictions and configuration changes require device checks.
- **Measurement boundary:** `NightModeDeviceTest` drives the sink directly, and silence tests drive the engine. They do not prove the real service's saved/live Night mode wiring or post-session limiter output, as D-40 explicitly records. These are verification limits, not evidence of a defect.
